# Feature catalog and status

The complete scope, known before the first line of architecture code. This is
the **destination**, reached through the staged releases in
`docs/ARCHITECTURE.md` and `BUILD-PROMPT.md` Part G — beginning with a
deliberately smaller 1.0.

**Part H requires the row for a feature to be updated in the same commit that
finishes it.** A row that says `done` for a feature whose control renders but
does nothing is a defect in this file as much as in the code — see the
wired-tools rule.

## Legend

| Status | Meaning |
|---|---|
| `—` | Not started. **Nothing exists** — not "exists but is not usable yet". |
| `partly` | Some of it exists and is proven; the body says which part and what is owed. |
| `wip` | In progress. Not reachable in the UI: the command registry's `when` predicate hides what does not exist yet. |
| `done` | End to end. Registered, contract entry validates, kernel proof **and** UI dispatch test both pass, strings are i18n keys, survives save and reopen. |

**THE CELL REFLECTS WHAT EXISTS; THE BODY SAYS WHAT IS USABLE.** Two rows have
now read `—` over delivered work — ADR-0006's PDF.js row, and drag-reorder after
its kernel half landed — both on the reasoning that nothing was reachable yet.
That reasoning is about usability and the cell is about existence, and a
not-started marker over work that exists gets rebuilt by whoever meets it next.
`partly` with a body reading *"kernel half only, no surface, not usable"* is
strictly more informative than `—` with the same body, and it is what stops a
planner counting a table of rows as a table of untouched work.
